# Отчёт агента — этап 1

Исторический отчёт этапов 1–2. Текущая реализация и результаты дальнейших проверок описаны в [отчёте этапа 3](AGENT_STAGE3_REPORT.md).

## Создано

Созданы `CMakeLists.txt`, `README.md`, `.gitignore`, `src/main.cpp`, QML-компоненты в `qml/`, скрипт `scripts/build.sh` и документы в `docs/`. Каталоги `shaders/` и `assets/icons/` подготовлены как места для будущих ресурсов.

## Реализовано

Минимальное Qt 6/QML-приложение с отдельным прозрачным тестовым окном, скруглённой локальной поверхностью Dock, горизонтальным рядом из пяти временных элементов и корректным закрытием при ошибке загрузки QML. Настоящие приложения, автоскрытие, системная интеграция, zoom и сложные эффекты намеренно не добавлялись.

## Проверка

Проверены версии: CMake 4.4.4, GCC 16.2.1, Qt 6.12.0; `pkg-config --modversion Qt6Quick` вернул 6.12.0. `XDG_CURRENT_DESKTOP=KDE`, `XDG_SESSION_TYPE=wayland`, то есть текущая сессия — KDE Plasma на Wayland. `./scripts/build.sh` успешно сконфигурировал и собрал приложение. Добавлен smoke-тест загрузки QML; после сборки он запускается командой `ctest --test-dir build --output-on-failure`.

Визуальный запуск в текущем терминальном окружении не подтверждён: при запуске с обычным backend процесс завершился с кодом 134 без диагностического вывода. В режиме `QT_QPA_PLATFORM=offscreen` приложение запускается, а `ctest --test-dir build --output-on-failure` завершился успешно: 1/1 тест. Smoke-тест подтверждает загрузку QML и корневого окна, но не заменяет визуальную проверку пяти элементов, прозрачности и скругления.

## Исправление загрузки QML

Причина ошибки `qrc:/MacGlassDock/qml/Main.qml: No such file or directory` — неверный ручной ресурсный путь в `src/main.cpp`. При политике `QTP0001 NEW` Qt регистрирует QML-модуль с базовым префиксом `:/qt/qml/`; в бинаре присутствует модуль `MacGlassDock` с типом `Main` (`qml/Main.qml`). Загрузка исправлена на `QQmlApplicationEngine::loadFromModule("MacGlassDock", "Main")`. Smoke-тест теперь завершается ошибкой, если `engine.rootObjects()` пуст.

## Ограничения и следующий шаг

Текущая `GlassSurface` — только визуальная заготовка и не является Liquid Glass. Визуальную проверку окна нужно повторить из полноценной пользовательской сессии KDE. Следующему агенту нужно отдельно исследовать безопасные способы blur/refraction в KDE Plasma 6/Wayland.

Приложение не меняет панель Plasma, системные конфигурации или автозапуск: в исходниках отсутствуют вызовы системной настройки и интеграции с Plasma.

Потенциальные проблемы настоящего Liquid Glass: отсутствие доступа к содержимому за окном в Wayland, различия compositor/KWin API, стоимость GPU-шейдеров, драйверные ограничения, масштабирование HiDPI и необходимость надёжного fallback.
